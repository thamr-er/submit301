interrupts

A signal that pulls the CPU away from what it's doing, makes it handle something urgent, and then puts it back exactly where it left off. Interactive demonstration of how the hardware/software interrupt cycle actually works.

01 · The Concept

what is an interrupt?

An interrupt is a signal sent to the CPU telling it to stop whatever it is currently executing and switch to a special routine that handles a more urgent or asynchronous event. Without interrupts, the CPU would have to constantly check ("poll") every device to see if it needed attention — wasting cycles. Interrupts flip that around: the device tells the CPU when something needs to happen.

When an interrupt is raised, the CPU finishes the current instruction, saves its state (program counter, registers, flags) onto the stack, looks up the address of the appropriate handler in the Interrupt Vector Table (IVT), and jumps to that Interrupt Service Routine (ISR). When the ISR finishes, the CPU restores the saved state and resumes the original program as if nothing happened.

Interrupts are what let your operating system be responsive. The keyboard, the timer, the disk controller, the network card — every one of them talks to the CPU by raising interrupts. Even system calls like read() and write() are implemented as software interrupts (INT 0x80 on x86, SVC on ARM).

03 · Taxonomy

types of interrupts

Interrupts fall into two broad families based on where they originate. Hardware interrupts come from outside the CPU and are asynchronous — they can happen at any moment. Software interrupts come from instructions and are synchronous — they happen at a known point in the running program.

04 · The Cycle

how an interrupt occurs

Every interrupt — whether it comes from a key press or a system call — follows the same fundamental sequence. The exact opcodes differ between architectures, but conceptually the steps below are universal.

01
Device raises an IRQ line
Hardware asserts an electrical signal on its interrupt line (e.g., the keyboard controller pulls IRQ1 high). For software interrupts, a running instruction triggers it directly.
02
CPU finishes the current instruction
The CPU does not stop mid-instruction. It completes the instruction it is currently executing to leave the machine in a consistent state.
03
CPU acknowledges and disables interrupts
The CPU clears the interrupt-enable flag so that the ISR itself is not interrupted by another maskable interrupt while it is starting up.
04
Save state onto the stack
The program counter (PC) and processor status (flags) are pushed onto the kernel stack. On many architectures the ISR pushes additional registers it intends to use.
05
Look up the ISR address in the IVT
The CPU uses the interrupt number as an index into the Interrupt Vector Table, which holds the entry-point address of every ISR.
06
Jump to and execute the ISR
Control transfers to the handler. The ISR services the device (reads the key, copies the disk buffer, advances the timer tick, etc.) and usually signals "interrupt handled" to the interrupt controller.
07
IRET — return from interrupt
The ISR executes a special return instruction (IRET, RTI, ERET). The CPU pops the saved PC and flags back off the stack, re-enables interrupts, and resumes the interrupted program — which never knew anything happened.
05 · Why It Matters

role in the OS

A
Multitasking exists because of timer interrupts
The scheduler runs because a timer interrupt forces the CPU out of the currently running process every few milliseconds. Without it, a process that never yields could hog the machine forever.
B
I/O is efficient because of device interrupts
Instead of the CPU polling the disk every cycle to ask "are you done yet?", the disk raises an interrupt when its transfer completes, letting the CPU do real work in the meantime.
C
System calls are software interrupts
When a user-mode program calls read(), it executes a trap instruction that interrupts the CPU into kernel mode, where the syscall handler can safely access privileged resources.
D
Exceptions are how the kernel takes over on errors
A divide-by-zero, an invalid memory access, or a page fault all raise exceptions. The kernel catches them, decides what to do, and either recovers (page fault → load the page) or kills the offending process.
