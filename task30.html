Unix System Calls · POSIX.1

write() — a handful
of bytes, kernel deep.

The thinnest possible primitive for sending bytes anywhere. You hand the kernel a buffer, a count, and a file descriptor; it does the rest. Files, pipes, sockets, terminals — they all start here.

/ 01

The signature.

ssize_t write(int fd, const void *buf, size_t count);
fd · int
A file descriptor — a small integer that names an open kernel resource. 0, 1, 2 are stdin/stdout/stderr; anything higher comes from open(), pipe(), socket(), etc.
buf · const void *
Pointer to the source bytes. Treated as opaque memory — text, binary, a struct, a JPEG, all the same to write(). The buffer is read, not modified.
count · size_t
The maximum number of bytes to transfer. The kernel may write fewer — even on success. Your code must check the return value and loop if it cares about delivering everything.
On success
return → n  where 0 ≤ n ≤ count

The number of bytes actually transferred to the kernel. May be smaller than count — that's a short write, not an error.

On failure
return → -1,  errno set

Inspect errno to learn why — EBADF, EPIPE, ENOSPC, EINTR, EFAULT, and others.

/ 02

What actually happens.

Your buffer lives in user space — memory the kernel doesn't normally touch. When you call write(), the CPU traps into kernel mode, the kernel uses the file descriptor to find the underlying file/pipe/device, and then copies bytes out of your buffer into a kernel structure (a page cache page, a pipe ring buffer, a socket send queue — it depends on what fd refers to).

Once the bytes are inside the kernel, write() returns. The kernel may not have actually sent them to disk or across the network yet — that happens asynchronously. (Use fsync() if you need a guarantee.)

For each open file descriptor the kernel also tracks a file offset. Each successful write() advances it by the number of bytes written, so the next call starts where the last left off. (Unless the fd was opened with O_APPEND, in which case the offset jumps to end-of-file before every write.)

/ 04

The partial-write trap.

write() is allowed to write fewer bytes than you asked for and still call it a success. If you don't handle that, your file ends up truncated and you don't even get an error. Always loop until done — or use a helper.

Naïve · may lose bytes
#include <unistd.h>
#include <string.h>

int main(void) {
    const char *msg = "important data\n";
    size_t n = strlen(msg);

    // What if write returns less than n?
    // Or returns -1? We just don't know.
    write(1, msg, n);
    return 0;
}
Robust · loops until done
ssize_t write_all(int fd, const void *buf, size_t count) {
    const char *p = buf;
    size_t left = count;

    while (left > 0) {
        ssize_t n = write(fd, p, left);
        if (n == -1) {
            if (errno == EINTR) continue; // retry
            return -1;
        }
        p    += n;
        left -= n;
    }
    return count;
}
/ 05

write() vs. fwrite()

write()  — syscall fwrite()  — libc
Layer Kernel system call. Direct trap into the OS. User-space library function. Internally calls write() in batches.
Operates on A file descriptor — an int. A FILE * stream returned by fopen().
Buffering Unbuffered. Every call hits the kernel. Buffered. Many fwrites batched into one write().
Header <unistd.h> <stdio.h>
Returns Bytes written, or -1. Items written (could be 0).
Best for Low-level I/O, pipes, sockets, fine control. High-throughput text output, formatted writes.
/ 06

Common failure modes.

EBADF
"Bad file descriptor"
fd isn't a valid open descriptor, or wasn't opened for writing. Classic cause: writing to a closed pipe-end or to fd 0 (stdin) when it's read-only.
EPIPE
"Broken pipe"
Writing to a pipe or socket whose reader has gone away. The kernel also raises SIGPIPE, which by default kills your process — install a handler or ignore the signal.
ENOSPC
"No space left on device"
The filesystem is full, or the user's quota is exceeded. You can get this even mid-stream after many successful writes.
EINTR
"Interrupted system call"
A signal arrived before any bytes were transferred. Not a real error — just retry the call. Robust code always loops on EINTR.
EFAULT
"Bad address"
buf points to memory the process can't read — null pointer, freed memory, or outside the address space. A programming bug.
EAGAIN
"Try again"
Only happens on non-blocking descriptors. The kernel can't accept any bytes right now without blocking. Wait (e.g. poll()) and retry.
